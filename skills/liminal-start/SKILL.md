# Starting with Liminal

Liminal Editor is a Blender add-on that makes Blender the level editor for a game. The game
owns the definition of what can be placed. Blender owns the placing. A `.lm` file carries the
result back. Your job as the assistant is to get a game from "nothing" to "export from Blender,
reload the game, see the level", then keep that loop short.

## The contract, which is all you need to hold in your head

```
game (TypeScript)                      Blender (Liminal Editor)
  entity registry  ──liminal sync──▶  _blender/entities.json  → Add menu, props, gizmos
  parseScene(.lm)  ◀──Export Level──  _blender/levels/<name>.lm  (glTF 2.0 + LM_entity, LM_geo)
```

- `entities.json` lists classnames, their props (with types, defaults, choices), colour and
  preview model, and viewport gizmos. The game writes it; nobody edits it by hand.
- A `.lm` is a standard binary glTF. Entity nodes carry `LM_entity` (classname, uid, props).
  Mesh nodes carry `LM_geo` (collision kind, tags). Any glTF loader opens it.
- Wiring between entities is string equality between a `destination` prop on the sender and
  a `source` prop on the receiver. Blender draws it as an arrow; the game dispatches on it.

## The pieces and who pays for what

| Piece | Role | From |
|---|---|---|
| Liminal Editor (Blender add-on) | the product: menus, props, gizmos, export | bought at https://liminal.lv |
| Liminal Bridge (Blender add-on) | lets this MCP drive Blender; optional, free | plugin repository releases |
| `@liminal/core` | types, registry, `.lm` reader, wiring | npm, MIT |
| `@liminal/cli` | writes the workspace, `liminal` command | npm, MIT |
| `@liminal/three`, `@liminal/collision-2d`, `@liminal/collision-3d` | adapters | npm, MIT |
| `liminal-mcp` | this plugin's MCP server | pip, MIT |

Say it plainly when it matters: the editor is paid and nothing works without it. Do not
suggest ways around that. Everything else is open source.

## Order of work

1. **Environment.** Run `/liminal:setup`. It checks Node, Python, Blender, the add-ons, the
   MCP server and the project, and prints fixes. Repeat until green.
2. **Game skeleton.** If there is no game yet, create one the user is comfortable with
   (Vite + TypeScript + Three.js is the common choice). Liminal does not care which renderer.
3. **Entities.** Write `src/entities.ts` with `defineEntity` and `createRegistry`, and a
   `liminal.config.ts`. Start with three to five entities: a player start, one light or prop,
   one trigger volume, one door or thing a trigger can affect. Read `liminal-entities` for how
   to make them good. Run `npx liminal sync`, then
   `python scripts/validate_entities.py _blender/entities.json` from this plugin.
4. **Bind Blender.** Editor preferences: add a Game Configuration whose Workspace Folder is
   the synced `_blender` folder (the one containing `.lmworkspace`), select it in the LM
   Toolkit sidebar (press N). Add > Entity now lists the registry.
5. **First level.** A floor plane, a player start, a light. Save the `.blend` somewhere in the
   project (not inside `_blender`, which is generated), Export Level. With the bridge running
   you can do all of this through the `lm_*` tools; `liminal-levels` is the workflow.
6. **Load it.** `parseScene` in the game, spawn entities by classname, build meshes and
   colliders from the geometry. `liminal-web` has the code for each adapter.
7. **Loop.** Export, reload, adjust. Add entities to the registry as the game grows; every
   `liminal sync` that changes the manifest bumps its revision and Blender asks to reload.

## Decisions to make early, with the defaults

- **Workspace folder:** `_blender` beside `package.json`. Commit `_blender/levels/` and
  `_blender/entities.json`; the rest is regenerated by sync.
- **2D or 3D:** the SDK supports both. A 2D game picks a plane (`xy` side-on or `xz` top-down)
  and uses `@liminal/collision-2d`. Decide before writing colliders.
- **Where authored `.blend` files live:** a `blender/` folder in the repo. Designers open them
  with the add-on installed.
- **uids:** the registry's `uid` is whatever your game resolves an entity from. Using the
  classname itself is fine for a web game.

## Things that look like bugs and are not

- Add > Entity is empty: no game configuration selected, or the workspace folder points at the
  project root instead of `_blender`. The LM Config panel says which.
- Blender asks to reload every build: the registry object was reordered, which changes the
  manifest. Append new entities; do not sort.
- The MCP cannot find Blender: the bridge add-on is not enabled, or Blender was started before
  the project folder existed. `lm_sessions` shows what it sees.
- A `.lm` loads but an entity's prop is missing: the level was exported before that prop was
  added. `scene.warnings` lists such drift; re-export the level.

## Other engines

Only the Web SDK is in scope here. A Godot plugin exists separately. For anything else, the
export format is documented at https://liminal.lv/docs and the `.lm` is plain glTF: a custom
importer is a day's work, and the entity registry can be written as JSON by hand or by a
script that follows the `entities.json` contract described in `liminal-entities`.
